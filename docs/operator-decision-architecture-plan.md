# Operator Decision Architecture Implementation Plan

> Historical implementation plan. Its default-policy and format-activation
> restrictions are superseded by the [current architecture](../README.md#architecture):
> Module 19 / Artifact 14 are active, STANDARD_LOCAL requires AGENT_RELAYED,
> and the retained protected WebAuthn signer is optional high assurance.
> The milestone descriptions below record the earlier implementation sequence.

## 1. Goal

Replace agent-carried authorization receipts with ledger-resolved, candidate-bound decisions for **new-format** migrations. Keep the decision ledger authoritative; give status, pending decisions, and run one fresh decision projection; make the review readable without asking the operator to inspect record files, copy identifiers, type challenge text, or restart the skill. A provider may display a review but cannot attest HUMAN authority. Enable `HUMAN_ATTESTED` writes only after the independent signer boundary passes real-host security sign-off. No implementation or host experiment is authorized by this plan.

**Current milestone scope (five-hour cap):** module records only. Module format **19** becomes `FORMAT_SUPPORTED` while production creation stays **18**. Artifact format **14** and direct-ledger artifact source/visual authority are **deliberately deferred to their own later milestone** and are not partially implemented here: artifact **13** remains the supported, active artifact path with unchanged behavior, artifact 14 is neither supported nor activated, and any dependency on artifact-14 semantics stays explicitly unavailable/blocked. This is a scope deferral, not a security downgrade — no invariant in §3 is relaxed.

## 2. Proven Current State

The engine does not need a restart after a recorded decision; the human → ledger → `decisionReferences` → agent-copied `decisionId`/`decisionDigest` → validation chain is fragile; the ledger is the authority. Provider-native interaction is **not trusted as human attestation**: a pseudo-TTY/tmux can drive terminal/TUI choices, and provider prompts and buttons do not establish human origin. Advertised form elicitation may be unavailable or hang; bound the wait and fail closed. A localhost WebAuthn signer and its host rendering require separate real-host acceptance before activation.

Repository touchpoints for implementation (locations, not additional trust claims): `packages/migration-engine/src/record-decision.mjs` derives candidates and appends chained lines; `resumable-migration.mjs` contains `createDecisionCandidate`, `decisionAppliesToCandidate`, `readRecordedDecisions`, `requireDecision`, `validateDiscoveryCompleteness`, `getMigrationStatus`, `advanceUnderLock`, format gates and integrity/history writers. `cli/run-migration.mjs` and `operator-approval.mjs` currently return receipts; `mcp-server.mjs` exposes the three tools and treats advertised elicitation as an inline recorder. The artifact path is separate in `artifact/artifact-migration.mjs`.

## 3. Security Invariants

1. The only authority for APPROVED/REJECTED is a verified append-only, hash-chained decision line for the **current, unique** candidate, under the correct ledger principal and policy. A chain detects edits but **does not authenticate a writer**: every `HUMAN_ATTESTED` line must carry a replay-verifiable WebAuthn proof, checked against the protected credential registry on every authoritative read, not just at append time. Verify existing `integrity.json` prefix anchors and history replay; never rewrite old lines or pins.
2. `HUMAN_ATTESTED`, `AGENT_RELAYED`, and `AUTO` are disjoint. Missing legacy principal/channel remains historical legacy HUMAN, **not** attested. Terminal TTY, MCP replies, hooks, auto-permission, and model/tool text can produce no `HUMAN_ATTESTED` line. `--mode auto` writes only AUTO to `decisions/auto-decisions.ndjson`; no implicit downgrade or cross-principal fallback.
3. Derive the complete canonical SHA-256 candidate digest from kind, subject, rationale digest, targets, record/worktree identity, current legacy revision/dirty digest, discovery/scanner digest and applicable path/visual evidence; bind the trusted policy identity/digest, ordered group members with each member's evidence, and lifecycle. Keep existing `APP-` IDs as display identifiers, not as the sole cryptographic binding. Re-derive under `withModuleLock` before append; compare the locked candidate and verify approval policy, authenticator proof and nonce there.
4. Explicit APPROVED authorizes only the named candidate when the principal meets its required level; explicit REJECTED is a signed, candidate-bound blocking outcome, never an approval. Reject becomes stale when candidate evidence changes; cancellation, dismissal, timeout and transport failure append nothing. Conflicting applicable outcomes or duplicate approvals fail closed rather than selecting an arbitrary line.
5. Browser assertion challenge binds a domain-separated protocol version, full candidate digest, APPROVE/REJECT, single-use nonce, record identity and expiry. Verify challenge, RP ID, exact origin, credential registration, UV flag and signature; atomically spend nonce and refuse replay/wrong digest under the append lock. An agent-writable credential registry, enrollment endpoint or signer process would void the boundary.
6. Enforce persisted registry/toolkit identity and actual worktree/cwd binding. Read-only status/pending never execute target-controlled code; the mutating run revalidates under its existing lock/journal. No valid decision alone closes a checkpoint.
7. For new-format groups, **one authoritative ledger entry** contains the complete ordered member set, one candidate digest, one result and (when attested) one WebAuthn assertion. Member-level projection is a view of that entry, never separate authority. A crash or torn append yields either the whole verified group decision or no applicable decision; duplicate or conflicting entries fail closed.
8. `requiredPrincipal` is resolved by an engine-owned default policy or an operator/admin-controlled protected policy, never by repository files, migration state, MCP input, provider capabilities or an agent-chosen mode. Judgment-bearing new-format kinds default to `HUMAN_ATTESTED`; a project-specific policy must have a trusted, pinned identity/digest and verified provenance. Missing, invalid or mismatched provenance blocks the decision. Only an explicit trusted operator/admin policy-change action may weaken authority, and doing so changes the policy digest and invalidates outstanding candidate bindings; it cannot retroactively authorize a weaker line.

## 4. Target Architecture

**Candidate generation → presentation → decision authority → ledger append → projection → validation → checkpoint advancement.**

- **Generation:** move the shared candidate assembly now in `record-decision.mjs` (`derivePendingDecisions`, artifact `deriveArtifactDecisions`) behind a read-only `decision-projection.mjs` boundary, reusing `createDecisionCandidate`, `decisionGroupFor`, `pendingVisualUnbackedCandidates`, `pendingTargetDriftCandidates`, and artifact `artifactOperatorDecisions`. Avoid a static ESM cycle into `resumable-migration.mjs`; keep the existing lazy artifact import or a runtime import from its status reader. A candidate is a proposal until its evidence and blockers are rechecked. Preserve concrete-target and runtime-observation validation; do not let an approval replace them.
- **Presentation:** `decision-presentation.mjs` renders one engine-owned review for CLI text, MCP/link and the signer. Include title, record/worktree identity, subject, why judgment is required, precise effects of Approve and Reject, all affected targets, proposal/rationale, evidence and provenance, all ordered group members, useful scanner/visual/drift details, and the full canonical candidate digest. A group is one reviewed act yielding **one authoritative ledger entry** for its complete membership; per-member screens are projections only. No raw ledger, JSON editing, ID transcription or challenge phrase for new format.
- **Authority:** an engine-owned closed policy table for new-format judgment kinds (`EXCLUSION`, `DEAD_CONFIRMATION`, `EDGE_RESOLUTION`, `ROOT_DECLARATION`, `TARGET_DRIFT_ACCEPTED`, `VISUAL_UNBACKED`, and applicable artifact decisions) requires `HUMAN_ATTESTED` by default. An engine-defined, provably derivable kind may be AUTO; `AGENT_RELAYED` may be allowed only by explicit trusted operator/admin policy, never by repository policy. Project-specific policies live outside agent-writable workspace/state under an operator-controlled trust root; pin and verify their identity and digest in protected configuration and the candidate/ledger binding. A trusted operator/admin change with an audit trail is required to weaken authority, and must produce a new policy digest and fresh candidates. Bad/missing provenance or pin mismatch fails closed. Show actual requirements in review/projection; never infer permission from repository files, `--mode auto`, MCP input, provider capability, or a weaker line. Historical formats retain their historical AUTO/citation semantics. Approval and rejection each represent a single decision; do not interpret host `decline` as REJECTED.
- **Ledger append:** extend `buildDecision`, `auditDecisionLedger`, `readDecisionLedger`, `ledgerHeadFor`, `appendDecisions` and `withOperatorApproval` in `record-decision.mjs`/`resumable-migration.mjs`. New lines get explicit schema `v: 2`, `principal`, `result: APPROVED|REJECTED`, trusted `policyId`/`policyDigest`, full `candidateDigest` and, for a group, the entire ordered member set including each member's evidence binding. Exactly one group line and one result are authoritative; an attested group uses one assertion bound to that whole digest/result. Attested lines additionally carry the public, replay-verifiable WebAuthn proof (`credentialId`, exact clientDataJSON, authenticatorData, signature and verification version; **no private keys**), checked with the protected registered public key on every authoritative read. A `verified: true` bit or verifier's assertion of success is never itself authority. Continue the current DEC chain in `operator-decisions.ndjson` for AGENT_RELAYED/attested entries, with strict principal parsing; AUTO retains its separate chain/prefix/anchor. Legacy lines keep their exact old serialization and digest. Append a complete single line under the existing lock; after a torn append, recovery rejects the incomplete line and never projects a subset as authoritative. Persist nonce consumption before appending (an interrupted claim needs a fresh review); verify complete line and existing prefix anchors on recovery. Only the companion's verified in-process result can request an attested append; an `ask` callback or argv value cannot claim that principal. Fail closed on malformed/unknown principal, invalid policy provenance, duplicate/conflicting group outcomes or forged result. Document that old `operator`/statement strings are historical descriptions, not proof of attestation.
- **Projection:** implement `projectDecisions({registryPath,moduleName})` as the canonical fresh, read-only view over current candidates, trusted policy, both verified ledgers and checkpoint state. It exposes each candidate's `requiredPrincipal`, pinned policy identity/digest, actual principal/result, ID/digest for **engine audit only**, review/link metadata and one of `AWAITING_HUMAN_DECISION`, `APPROVED_APPLICABLE`, `REJECTED`, `STALE`, `READY_TO_ADVANCE`, or `LEGACY_COMPATIBILITY_ACTION_REQUIRED`; additionally expose `checkpointAdvanced` separately. For groups, per-member views point to the single complete verified group line and cannot independently become authoritative. `READY_TO_ADVANCE` means the **decision gate** is clear, not that a potentially executable step validation ran in status. A valid append is immediately `APPROVED_APPLICABLE` even while `state.json` is unchanged. A stale line stays visible but cannot satisfy a changed candidate. For new format, remove `decisionReferences` as an agent instruction/output; if wire compatibility demands the key, emit an empty/deprecated field only on new records. `getMigrationStatus`/`migration_status`, `pendingDecisionCandidates`/`migration_pending_decisions`, and `runMigration`/CLI consume the **same fresh projection**, not three independent pending/approved tests. MCP `runTool` reports a newly read status after append.
- **Validation:** add one policy-aware `resolveApplicableDecision` in `resumable-migration.mjs`, shared with the projection and artifact validator. For new records it resolves exactly one applicable APPROVED line directly from the ledgers using the full candidate and trusted-policy binding, without reading receipt fields from authored JSON; a grouped member resolves only through its complete group entry. A current REJECTED blocks with its reason/identity. Preserve existing `requireDecision` byte-for-byte behavior for old-format cited rows. Cover module roots, DEAD/EXCLUSION files, finding edges, visual unbacked entries (`validateVisualAcceptance`) and drift (`classifyTargetDrift`/FINALIZE); no sibling caller may bypass principal checks. Artifact source/visual decisions are **out of the current milestone**: they stay on the artifact-13 legacy citation path, and the artifact validator is not routed through this resolver until the deferred artifact-14 milestone.
- **Checkpoint:** `advanceUnderLock` captures the validated set of `{candidateDigest, decisionId, decisionDigest, policyId, policyDigest, principal, result}` consumed by that advance in the `STEP_COMPLETED` history event and journal/integrity material (`renderIntegrityNow`/`prepareHistoryEvent`); a group contributes one complete decision identity, not a partly recorded member set. Do not mutate pinned classification/old history. On crash/replay, the same event set is recovered once with its hash-chain and ledger-prefix anchors. Artifact `buildAdvanceTransaction`/`writeTransaction` keeps its existing artifact-13 transaction/history shape unchanged in this milestone; consumed-identity journalling for new-format artifact records belongs to the deferred artifact-14 milestone. Ordinary `getMigrationStatus` remains observational.

## 5. Compatibility Boundary

Module records: retain `RESUMABLE_CONTRACT_VERSION = 5`; register **19** as the next supported format after **18**, add `usesDirectLedgerDecisions(state)` at 19, and register **18 → 19** in `FORMAT_UPGRADERS` (floor 17, `assertRegistryCoverage`/`nextIncrement`). Newly bootstrapped 19 records author classification `version: 2` with rationale/evidence/targets but **no** `decisionId`/`decisionDigest` (also no such fields on roots, findings or new visual unbacked entries). Reject these receipt fields on v2 to prevent ambiguous authority. Select behavior from the persisted **record format**, checking classification schema consistency; never promote an 18-or-earlier pinned classification, discovery pin or decision to new semantics by ordinary advance. A completed/pinned old record remains historical; an eligible unfinished 18 record needs an explicit, journalled 18 → 19 transition **only before** its decision-bearing artifact is pinned, with preview/confirmation and no invented approval. Otherwise offer `LEGACY_COMPATIBILITY_ACTION_REQUIRED`: resume under old citation rules or deliberately start a new record. Preserve `stampedFormatVersion`, `NON_PROMOTING_FORMAT_VERSIONS`, `FORMAT_FEATURES` and existing pre-17/17→18 adoption behavior; format 19 must not accidentally become a self-healing stamp.

Artifact records — **deferred, not implemented in this milestone.** `artifact/artifact-migration.mjs` keeps stamping **13**, keeps floor **13** and keeps its empty `ARTIFACT_FORMAT_UPGRADERS`. Format **14** is **not registered, not supported, not activated** and no 13 → 14 upgrader, direct-ledger artifact resolver or artifact `v: 2` classification is written now; artifact 14 must not be partially implemented. Artifact 13 therefore keeps its exact historical lifecycle, citation rules (`decisionReferences`/`recordedDecisionId`), transaction/history shape and fixture bytes. A module-19 parent may **not** reinterpret an artifact-13 decision as new direct-ledger authority and may not demand model receipt copying for one: a child whose decision authority is not expressible under the module-19 path is surfaced as a typed `LEGACY_COMPATIBILITY_ACTION_REQUIRED` compatibility action, never laundered into new authority. Any code path, option or contract that would require artifact-14 semantics must fail closed as explicitly unavailable/blocked until the dedicated artifact milestone implements it. The target shape described in §4 for artifact records stays the design of record for that later milestone only.

**Two independent controls, never inferred from a version constant:** `FORMAT_SUPPORTED` means the engine can read, validate, test and, when explicitly selected, create a format; `FORMAT_ACTIVE_FOR_NEW_MIGRATIONS` determines the default creation format. In this milestone module **19** becomes supported while module creation defaults to **18**; artifact **13** is both the only supported and the active artifact format. Ordinary creation, module-child creation and artifact standalone creation all consult the activation control, not the highest supported registry entry. Explicit module-19 selection is permitted only in controlled test/pilot contexts under the same fail-closed principal policy, never as an implicit production default. Module-19 support ≠ activation: after real-host signer sign-off, a **separate explicit security/release decision** may activate new creation defaults, verifying signer readiness, policy provenance, package/provider release checks, fallback behavior and rollback; sign-off alone does not flip a default or rewrite existing records. `HUMAN_ATTESTED` write activation remains its own explicit security gate after real-host sign-off; neither format support nor format-default activation substitutes for it. Shipping module 19 does not imply attested decisions are possible — pending requests fail closed, with a link only if a companion is actually ready.

## 6. Implementation Phases

**Planning verdict: READY under the five-active-hour cap, with new-format artifact authority deferred.** Phase 1 is complete and approved: step 1.1 took about 11 minutes, 1.2 about 23 minutes, and 1.3 about 17 minutes, for about **51 active minutes**; step 1.3 reported **449 relevant tests passed, 0 failed**. Its current worktree changes are the baseline. They provide v2 principal/result/full candidate digests, protected-policy resolution, strict ledger parsing, and a single crash-atomic group line. They do **not** yet select module-19 semantics from a persisted record, route the module validators through direct authority, or share one status/pending/run projection.

The sequence below is the **module-only** milestone: four complete parent phases totalling **300 active minutes (5 h)**. The earlier 7-hour lower bound is reduced to 5 hours by one scope decision — deferring artifact format 14 and direct-ledger artifact source/visual authority in whole (old Phase 3 removed, not thinned) — and by consolidating module checkpoint identities into Phase 2 and the module contract/regression work into one gate. No security invariant is weakened; artifact 13 simply keeps its existing behavior.

One prompt executes one entire parent phase, reports and stops for review; child steps get no separate prompts and no intermediate approval. **The per-phase times are hard ceilings, not work targets: if a phase finishes early, stop and report — do not start the next phase with the spare time.** Stop early also for a genuine blocker. Estimates include that phase's focused checks. Paths are under `packages/migration-engine/` unless stated otherwise.

Excludes all artifact-14 work.**

**Primary files:** `src/resumable-migration.mjs`, `src/record-decision.mjs`, `src/core.mjs`, `test/unit/migration-contract.test.mjs`, `test/unit/format-upgrades.test.mjs`, `test/unit/live-history-replay.test.mjs`.

**Verification:** changed evidence invalidates authority; weak/rejected/conflicting lines fail closed; receipt fields rejected on v2; old citations, pins and `integrity.json` anchors unchanged; creation default still 18; interrupted upgrade and crash replay recover one consumed identity set.

**Complete when** no module validation caller can bypass the current policy/candidate binding, an old record is neither silently promoted nor frozen, and no artifact behavior changed. **Ceiling: 75 min.**

## 7. Required Work and Deferred Gates

**Required before claiming a safe supported module-19 architecture:** complete phases 2–5 — format-gated direct module validation, compatible old-record behavior, journalled consumed module identities, one fresh projection, safe presentation, fail-closed signer denial, contract alignment and regression. These are inseparable from internal consistency and total **300 active minutes**. Phase 1's denial of unverified `HUMAN_ATTESTED` on both append and read is reusable now.

**Deferred work — none of the following is implemented, and none may be treated or reported as complete:**

1. **Artifact format 14 and direct-ledger artifact source/visual authority.** Required before artifact 14 can be supported or activated. Until then artifact 13 is the only artifact path, artifact 14 is unavailable, and any dependency on artifact-14 semantics fails closed. Artifact 14 must not be partially implemented.
2. **Production WebAuthn signer implementation and activation** — verifier, nonce store, protected companion, operator-controlled launcher. Required before `HUMAN_ATTESTED` becomes writable.
3. **Real-host signer/authenticator acceptance** — installed-provider behavior, physical/platform authenticator, browser/OS trust, protected enrollment/service and credential history, real-host review-to-challenge binding, security sign-off.
4. **Production-default activation of module 19 (and later artifact 14)** — a separate release/security gate verifying signer readiness, policy provenance, package/provider checks, fallback and rollback.

Items 2–4 are outside the 300-minute estimate; counting them would only increase it. Provider-native UI remains presentation only. Until a reviewed signer and real-host sign-off exist, attested lines are neither minted nor accepted; a link is shown only if a real companion is ready, otherwise the request is typed blocked. Module 19, once supported, still defaults to 18 in production, and artifact creation stays 13.

**Minimum deferral analysis:** the 7-hour lower bound is reduced to 5 hours by removing exactly one coherent unit of work — the whole artifact-14 milestone (old Phase 3, ~90 min) — plus consolidation of module checkpoint identities into Phase 2 and one combined contracts/regression gate (~90 min of former Phase 4/6 overlap). Nothing mandatory for the *module* path was thinned: both the shared projection and its regression remain in full. This is the minimum safe deferral because artifact 14 is the only scope boundary that can be removed whole, leaving no half-built format and no cross-format authority ambiguity. Old records keep working under their historical gates; format support, signer write activation and production-default activation remain separate gates.

## 10. Risks

1. **False authority promotion (critical):** current `TERMINAL`/`ELICITATION` entries are not attested; legacy lines and `AUTO` must never be reinterpreted by the new resolver. Prevent via persisted format + ledger-v2 principal gates and negative tests.
2. **Signer provenance (critical):** localhost and WebAuthn UV do not isolate an agent sharing the operator's UID, browser automation or credential enrollment. Require protected service/credential store and real-host physical/platform/UV review before enabling; no fallback to weaker principal.
3. **Ledger/schema and checkpoint replay (high):** v2 fields change line digests; old DEC chain and `integrity.json` anchors cannot be rewritten. Journal consumed identities with the checkpoint and test crash gaps, torn single-entry group append/recovery, duplicate/conflicting outcomes and nonce persistence; never project a partial group.
4. **Compatibility (high):** module formats 4–18 and artifact format 13 have pinned/cited artifacts, multiple format-upgrade gates and released consumers. Admit old records without silent promotion, preserve old fixtures/fields and explicitly report impossible upgrades; never rewrite consumer worktrees.
5. **Provider capability misreporting / hanging (high):** advertised MCP form support does not guarantee a functioning UI; use allowlist/real-host evidence, bounded timeouts, late-response cleanup and plain-link or typed-blocked fallback.
6. **Browser/platform and crypto/WebAuthn complexity (high):** secure-context/RP/origin behavior, COSE algorithms, UV policy, counter-zero authenticators, registration/revocation and hardware-specific UX need reviewed verifier dependency plus sign-off; avoid homegrown WebAuthn parsing.
7. **Migration-resume regressions (high):** status is read-only, run performs at most one advance, module and artifact journals differ, late decisions have ledger-prefix rules, and older decisionReferences are contractual. Require same-session and crash/replay tests before release.
8. **Review integrity (high):** HTML injection, misleading host links, candidate updates while review open, and group-member omissions can trick an operator. Render inert full review from the same digest the signer verifies and rederive under lock.
9. **Default/policy downgrade (critical):** registering module 19 does not change the module-18 / artifact-13 production creation defaults, and artifact 14 is not registered at all; mutable repository/state/provider inputs cannot lower `requiredPrincipal`. Check explicit creation gates and protected policy pin/provenance on every authoritative path, with negative downgrade tests and separate security/release activation.
