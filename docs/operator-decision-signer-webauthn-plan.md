## Verdict and current baseline

**BLOCKED for production activation until an isolated deployment passes security acceptance; implementation design is ready for that deployment. Do not implement from this plan without approval.** The missing primitive is an OS-enforced operator/service security domain that the migration agent cannot administer, read, impersonate, or debug, including its browser profile and protected signer state. A WebAuthn key alone does not supply that separation or attest that a person read the review. Provision this domain, then demonstrate it in the separate real-host gate before enabling writes. If no such domain can be provided, keep `HUMAN_ATTESTED` non-writable and module 18 the production default.

Approved module-only baseline: 1,013 passed, 0 failed, 1 skipped **as reported for the prior milestone, not rerun here**. Module 19 is supported and ledger-resolved/candidate-bound, but production creation stays at 18; status/pending/run share one fresh projection; provider presentation is not attestation; missing signer is typed `SIGNER_UNAVAILABLE`; artifact 13 remains supported/default and artifact 14 unavailable. This document does not authorize implementation, host experiments, release, or activation.

## Trust boundary and human authority

**Trusted, only after protected installation and host acceptance:** (1) the verified, read-only installed engine build for deriving current module-19 candidates, trusted policy and review, then for checking/appending them; (2) a small separately privileged signer/companion serving the review, creating challenges and owning nonce/credential/audit transactions; (3) an operator-only browser instance/profile on its exact trusted origin, with no agent-controlled extensions, debugging port, profile files or automation access; (4) a registered hardware authenticator whose non-exportable credential performs UP and fresh UV for this request; (5) an OS-protected credential registry plus durable challenge/nonce/claim store; (6) a separate operator/admin enrollment and revocation boundary. Trust the authenticator's signed result **and the verified browser origin**, not mere physical proximity or a localhost address. Authenticator UV proves local user verification, not comprehension or transaction-display binding; review comprehension remains an operator/browser/OS assumption to test.

**Untrusted even when apparently interactive:** model, provider, provider capability declarations and hooks, MCP transport/responses, terminal/TUI and tmux/pseudo-TTY, repository/worktree and migration files/state, agent-supplied argv/env/cwd, provider links, page parameters, and arbitrary localhost clients. They can request a review or cause a denial, but cannot enroll, change policy/credentials, generate an accepted proof, spend a nonce without that proof, or activate writes. The installed engine/companion binaries, dependencies, browser profile, trust configuration, and privileged data must be outside agent-writable paths and signed/verified at installation; an imported module from this worktree is **not** a trusted verifier. The target worktree lock only serializes cooperating mutations.

The agent can invoke `node` with `NODE_OPTIONS=--import/--require`, preload code, alter PATH/cwd or run its own engine clone. Therefore **an agent-launched engine process is not itself the root of human authority**, even when its source files are installed read-only. The protected service must be launched by the OS manager with pinned runtime/bundle and sanitized env, rederive review/candidate/policy itself, and independently verify every claim and exact appended line. A caller's toolkit identity string, self-reported successful check or IPC peer UID cannot replace that validation. The official engine should reject unsafe launch overrides, but system security cannot rest solely on that rejection; an injected clone may lie to a provider, yet cannot produce a COMMITTED protected claim or a replay-verifiable attested line without the operator-isolated ceremony. An agent that can actually modify the protected service/browser or trick UV into completing for a hidden result invalidates the premise and blocks sign-off.

Provision on a managed Linux desktop with a non-admin migration-agent UID, distinct operator desktop UID, and dedicated non-login signer-service UID. The agent must have no sudo/root, docker/container host escalation, ptrace of the service/browser, access to operator home/session bus, protected admin socket, or browser automation/debug interfaces. The service needs narrowly granted read access to migration data and write access only to its protected store; the engine's existing write path appends to the migration ledger. Expose a **separate, narrow unprivileged engine RPC** only for begin/read/verify-and-claim/finalize: its caller supplies no trusted facts, its service rederives issue bindings and independently verifies signature, nonce and proposed line before protected mutation; no enrollment, policy edit, registry overwrite or activation method is reachable there. Read-only verification returns a service-authenticated verdict on the exact raw line/proof, never a writable `verified` field. Authenticate the operator independently of navigation to a review link (protected OS desktop login plus operator-only browser session); a link is a locator, **never a bearer authorization**. If the account or platform cannot enforce these conditions, **BLOCKED**, not “localhost is trusted.”

`HUMAN_ATTESTED` qualifies **only** if a v2 `DEC-` operator-ledger line has `principal: "HUMAN_ATTESTED"`, explicit `result: "APPROVED"` or `"REJECTED"`, current module-19 candidate/policy/group binding, a complete proof using protocol version 1, and a matching protected **COMMITTED** nonce claim for the exact line digest, all reverified on read. Unknown/missing proof or verifier version fails closed. `AGENT_RELAYED`, legacy HUMAN/TERMINAL/ELICITATION, `AUTO`, native provider UI, terminal text, MCP replies and model/tool prose cannot be promoted by labels, callbacks, env, argv, or a stored `verified` bit. A trusted admin policy may explicitly allow `AGENT_RELAYED` for some kind; that remains `AGENT_RELAYED`, not attestation. A forged line with a valid hash chain is not a signed line.

## WebAuthn challenge and verification

**Protocol `amt.operator-decision.webauthn.assertion.v1`.** Preserve the engine's existing `candidateDigestOf(candidate)` algorithm; do not shorten it to an `APP-`/`DEC-` display ID. For each review/action construct this exact JSON object with **these keys in this order**, no optional/extra keys, UTF-8 `JSON.stringify` escaping, no whitespace, ASCII lowercase `sha256:` digests, decimal safe-integer millisecond times, NFC-normalization forbidden (use existing engine-derived strings verbatim):

```json
{"protocol":"amt.operator-decision.webauthn.assertion.v1","recordKind":"module","migrationId":"<state.migrationId>","module":"<canonical module name>","projectRoot":"<trusted resolved absolute target root>","candidateDigest":"sha256:<64 lowercase hex>","result":"APPROVED|REJECTED","requiredPrincipal":"<engine-resolved principal>","policyId":"<engine-resolved trusted policy ID>","policyDigest":"sha256:<64 lowercase hex>","groupMembersDigest":null,"groupMemberCount":0,"nonce":"<base64url 32 random bytes, no padding>","issuedAtMs":0,"expiresAtMs":0}
```

For a group replace `groupMembersDigest` with `sha256:` + SHA-256 hex of UTF-8 `JSON.stringify(group.boundTo.members)` **as derived by `createNewFormatDecisionGroup`**, preserving array order and every member's `boundTo` evidence; set `groupMemberCount` to its array length. For a singleton, require exactly `null` and `0`. `requiredPrincipal` is the actual trusted-policy requirement (normally `HUMAN_ATTESTED`); a valid attested proof may satisfy a policy that explicitly permits a weaker principal, but the requirement may never be supplied by the caller. The outer `candidateDigest` already commits to the whole group, ordered membership, policy, lifecycle and evidence; the extra group digest/count makes the review/proof's membership explicit. Compare `migrationId` with the persisted `state.migrationId` and the trusted canonical resolution at issue and under lock; reject absent or conflicting identities, never trust a supplied path. Verify that `projectRoot` and module resolve to this specific persisted record and pinned toolkit identity.

Let `P` be the UTF-8 bytes of that fixed-order JSON **with actual values**. Let `C = SHA-256(UTF-8("artifact-migration-tools/operator-decision/webauthn/assertion/v1\n") || P)` (32 bytes); `challenge = base64url(C)` without padding. This 32-byte challenge is the `PublicKeyCredentialRequestOptions.challenge` bytes; the browser's `clientDataJSON.challenge` must equal that exact base64url string. Save the payload and raw assertion for verification, never accept a client-provided payload as expected bytes. The authenticator signs `authenticatorData || SHA-256(raw clientDataJSON bytes)` per WebAuthn; it does **not** sign the plain `APP-` ID, HTML, a JSON string supplied by the model, or just a random token. Domain, protocol, result and all bindings are inside `P`; any encoding/version drift blocks. The companion recomputes `C` from the same fresh engine-owned review for the selected explicit action. If using SimpleWebAuthn option generation, override its generated `challenge` with this precomputed base64url value and verify against the **same base64url value**; do not pass a base64url string as its custom UTF-8 challenge and accidentally double-encode it.

After inspecting Node/ESM/package constraints, **recommend pinning a reviewed `@simplewebauthn/server` release** (its 14.0.x documentation/API and npm metadata support Node 22+, `verifyAuthenticationResponse`/`verifyRegistrationResponse`; version and transitive dependency audit belong to implementation) and, only if needed for browser JSON conversion, matching `@simplewebauthn/browser`. Native `node:https` suffices for a tiny web endpoint and `node:crypto` for SHA-256/randomBytes; do **not** write a COSE/CBOR/authenticatorData parser or a signature implementation. Pin library versions in `pnpm-lock.yaml` and exercise Node 22 and the staged release; reject if its shipped behavior fails the required policy rather than loosening policy. Library reference: <https://simplewebauthn.dev/docs/packages/server>, <https://simplewebauthn.dev/docs/advanced/server/custom-challenges>.

At registration allow **COSE ES256 (`-7`) only**, with platform/hardware behavior accepted only if it actually meets the chosen deployment policy; record the reviewed COSE public-key bytes, algorithm and credential ID. Other algorithms and unknown extensions block until separately reviewed. At assertion call the reviewed verifier with **one** exact `expectedOrigin`, **one** exact `expectedRPID`, expected challenge string, registered public key/credential ID, `requireUserVerification: true`, `expectedType: "webauthn.get"` and default UP checks; reject `crossOrigin: true` (including iframe/top-origin paths), missing UP/UV, wrong credential/type/algorithm, altered signature/data, unexpected flags/extensions, unregistered/revoked credentials or impossible backup-state changes. Do not use origin/RP allowlist arrays or skip UV. Verify signature and authenticatorData RP-ID hash through the library; assert returned credential ID, RP ID, origin, UV and expected counter transition. Require exact registered `userHandle` if one is configured; otherwise require absent/null, not an arbitrary operator identity claim.

Origin/RP are **protected deployment constants**, not env/argv/worktree values. Proposed managed-Linux deployment: provision a TLS certificate and protected key for `https://operator-decision.localhost:44321`, RP ID `operator-decision.localhost`, bind loopback only and pin this exact origin/port in the protected installation (or choose another single concrete trusted origin in an explicit admin deployment decision **before enrollment**). No HTTP downgrade, wildcard origin, CORS, silent port change or plain `http://localhost` production fallback. Validate actual browser/RP behavior in acceptance; if secure-context or WSL-to-browser behavior differs, block, do not auto-relax origin. Strict Host/Origin and fetch-metadata/CSRF checks, no framing, no injected scripts, no third-party resources, secure HttpOnly SameSite=Strict operator-session cookie and TLS protect the browser endpoint; OS/operator session separation, not those headers alone, is the security boundary.

## Nonce lifecycle and crash safety

Protected service generates `randomBytes(32)` after the operator opens the **independently derived** review and chooses exactly one result. Persist `{nonce, payload P, challenge C, session/credential allowlist, issuedAtMs, expiresAtMs, status: ISSUED}` in its OS-protected durable store before sending options to the browser; 120-second max challenge lifetime and bounded overall review session (e.g. 10 minutes). A new action gets a **new** nonce; changing result, candidate, policy or group invalidates the old session and needs a fresh review. Enforce protected-server time and expiry **when claiming**, not when replay-reading an older committed proof. Unique nonce index, strict byte equality, no bearer nonce authorization; reject wrong candidate/result/record/policy, expiration and duplicates. Cleanup may delete expired **unclaimed** sessions only after recording expiry in protected audit; keep every spent claim/history needed for authoritative rereads.

Under the existing module lock, ordering is: rederive candidate/policy and line head → check candidate/review equality and no duplicate/conflict → construct tentative **single** line/proof/digest → service verifies full WebAuthn assertion against issued challenge and protected credential state → **atomically claim** nonce and advance the credential counter in one durable protected transaction, recording exact tentative `decisionLineDigest`, proof hash, counter-before/after and claim time as `CLAIMED` → append one newline-terminated line with O_APPEND and `fsync` file (and directory as needed) → request protected service to mark that exact line/nonce `COMMITTED` after checking its durable on-disk bytes, expected record path/head and proof through a no-follow handle → only then report success/fresh projection. Registry transaction uses a durable transactional store (e.g. protected SQLite with UNIQUE nonce, `BEGIN IMMEDIATE`, WAL and `synchronous=FULL`), not worktree JSON, process memory, or the cooperative module lock. Claim acknowledgment is after durable commit; **never roll a claim back** after a failed append. Protect claim and counter with one per-credential serialized transaction across records, not only the per-module lock.

Authoritative reads require `COMMITTED` and exact proof/line-digest match. Crash before protected issuance: no valid challenge; after issuance: expires unused; after verification but before durable claim: no authority, retry only if nonce demonstrably ISSUED and unexpired (simpler policy: cancel and start new review); during/after claim before append: nonce spent, **never** reuse; after complete append but before durable service `COMMITTED`: line is **not authority** and blocks further reads/appends, not auto-promoted. Service crash between commit and reply also leaves a blocked, already-spent claim. An authorized admin can reconcile only by inspecting the exact complete/fsynced line, matching protected claim and proof, existing prefix/head and audit; otherwise quarantine/fail closed and require a new candidate/review. No automated retry that writes a second line or reclaims a spent nonce; never rewrite existing anchors. A torn line blocks the whole ledger pending authorized non-destructive repair; never project its group members. After durable COMMITTED, a lost HTTP/IPC response is harmless: reread yields exactly the one applicable line. Protected-store unavailable or corrupted ⇒ attested reads and writes block; it is not a reason to use `AGENT_RELAYED`.

Counters: the reviewed verifier checks the current protected last counter at claim; positive values must strictly increase, a fall or non-incrementing positive value blocks/quarantines the credential. An authenticator that reports zero consistently is allowed **only if enrolled/admin-accepted as counterless** and still supplies unique nonce, UP/UV and signature; zero offers no clone detection. Zero→positive begins monotonic tracking; positive→zero is a failure requiring admin investigation/re-enrollment. Per-claim protected counter-before/after snapshots let replay verification use the historic counter state, not compare an old valid assertion with today's larger count; the protected audit verifies transitions/uniqueness. Revoke a suspect zero-counter credential if the host threat test cannot justify it.

## Protected credential registry and enrollment

Store credentials, status, public COSE key bytes, alg, RP/origin, operator binding, registration response/verification metadata, registration revision, counter history and immutable revocation/rotation events in a service-owned OS-protected store **outside** repository, target root, ordinary migration state, home of agent UID and staged toolkit worktree (proposed `/var/lib/artifact-migration-tools/operator-signer/`). Only the dedicated service UID may transact; trusted admin owns installation/configuration, TLS key and enrollment control; agent UID gets neither directory traversal nor a writable admin socket. Public keys are not secrets, **provenance and immutability are the protection**. Protected audit includes who authorized each enrollment/revocation, time, previous revision, reason, credential/public-key digest and claim history. Back up/restore with admin custody and rollback protection; a restore missing previously committed nonce claims or credential revocations is unsafe, blocks rereads until reconciled. Never let a repo file or MCP tool name the registry path or public key used for verification.

Enrollment is a separate admin action in a protected operator browser/session plus an out-of-band admin authorization (not a provider/terminal flag). Create a fresh registration challenge on the pinned origin/RP; verify the registration response, challenge, UP/UV, key/algorithm and credential ID using the reviewed library; bind it to the approved human identity, security-key/backup policy and protected audit before accepting decisions. A mere credential registration UI exposed to localhost is a privilege-escalation endpoint. Require admin-approved physical possession and UV; prevent self-enrollment by the agent. Rotation enrolls the replacement under the same checks before retiring the old key, preserves old public keys and history for rereads, and never silently reuses counter or nonce state. Retirement disallows **new** claims but previously committed signatures remain historically checkable; compromise **revocation** invalidates affected attested authority on current reads until an admin reviews/re-attests decisions (fail closed; no erasure of audit history). Test these semantics explicitly.

Open installed executable/config, registry DB and parent directories using owner/mode checks and no-follow/open-by-handle patterns; reject symlinks, world/group-writable ancestors, mount/path substitution, untrusted migrations as service configuration, and hardlink/rename attacks. Use an OS service manager and an installed immutable release, not `node` loading agent-modifiable JS. Filesystem ACLs must be assessed on the *actual* deployment filesystem and across any host/guest interoperability. If the agent can escalate to an administrator or access the operator/service domain, nominal root ownership and mode bits do **not** keep it out: **production enrollment/registry remains BLOCKED**. Cross-machine transfer is admin-controlled export of public registry + complete spent/revocation audit and same RP/origin policy, authenticated and rollback-checked; private authenticator keys are never copied. If the new machine cannot keep origin/RP and trust root, re-enroll and re-attest rather than accepting old proof as current authority.

## Signer architecture and review integrity

**Choose a separately privileged, operator-launched/OS-managed, bounded companion with a small HTTPS loopback review endpoint**, not an engine subprocess under the agent's UID and not a provider/MCP-hosted page. Browser WebAuthn requires a secure origin; a CLI-only short-lived process cannot safely collect browser assertions or protect enrollment/state. Node's native HTTPS suffices; pin one origin/cert, use a protected operator browser profile and a private protected admin/service IPC surface. Companion can be short-lived per operator session and exits on idle timeout; its durable registry/nonce store survives restarts. Host sees only a review URL or explicit `SIGNER_UNAVAILABLE`; readiness is authenticated against the installed companion, not provider-advertised capability. An untrusted client may request a review by record identity but cannot choose the facts, policy, result, challenge or operator; the service reopens them via installed engine readers and the protected registry. The URL/opaque session handle alone cannot approve.

Page data comes from `reviewFor`/`renderDecisionReview` and the fresh module-19 projection; show module/record/worktree, kind, subject, all targets, untrusted rationale/evidence/provenance, pinned policy/required principal, full candidate digest and, for a group, **every ordered member**, member evidence and group digest/count. Render untrusted strings as `textContent` (or strictly escaped HTML), no `innerHTML`, raw Markdown/HTML, active links from evidence, embedded resources, or script/event handlers; set restrictive CSP, no-store/cache, no framing, no third-party content. Provider links are navigational hints only; display the exact pinned origin and warn on mismatches. Operator-only browser session/OS desktop must remain isolated from agent control; a browser automated under the agent's same account is not a human attestation boundary.

Page opens with **no pending credential request**. Explicit separate **Approve** and **Reject** controls display the chosen `APPROVED`/`REJECTED` in large plain text alongside the full digest and group member list **before** calling `navigator.credentials.get()`. A click does not decide automatically; it asks for fresh UV+UP, and dismissal/cancel/close/timeout/transport error appends nothing. Recompute candidate/policy/group before issuing a challenge and once more under the module lock when proof returns. If changed, invalidate page and nonce, require a new review; never silently refresh digest or reuse an old signature. Bind browser session to operator login and a short expiry; disable caches/back-button replay and reject concurrent result changes. Companion returns **raw verifiable assertion material only** to the engine; its JSON `success`, `verified`, user-facing button state and MCP response are never authority. Engine performs/requests authoritative proof check and durable nonce claim under the lock. No direct provider-native HUMAN trust, fallback TTY approval, or automatic decision.

## V2 ledger integration and authoritative reads

Keep the existing v2 `DEC-` line shape and hash/anchor calculation. Add exactly one attested-only public field `webauthn` containing `{verificationVersion:1, credentialId, nonce, clientDataJSON, authenticatorData, signature, userHandle:null}`; strings for binary assertion components are **canonical unpadded base64url of the exact received bytes**, with strict length bounds and no duplicate/unknown keys. Preserve other existing v2 fields (`result`, full `candidateDigest`, `policyId`/`policyDigest`, `boundTo`, group membership); no private key, PIN, session cookie, trusted `verified:true`, or secret challenge-store contents in the ledger. Optionally include a non-authoritative `origin`/`rpID` display field only if read derives and compares it from raw signed data; avoid the duplicate by default. Line digest commits to proof and existing chain head; the protected claim is keyed to that digest and nonce.

On **every authoritative read** (`readOperatorDecisions`/`readRecordedDecisions` feeding `projectDecisions`, validation, checkpoint advance, ledger audit/`--verify`), schema/chain/prefix checks still run; for each `HUMAN_ATTESTED` line fetch its protected registered public key/history and COMMITTED claim, reconstruct fixed-order payload from the line's candidate/policy/group + protected issued challenge/record identity, recompute `C`, verify raw WebAuthn via reviewed dependency, signed result and claim/line digest, enrollment validity at claim and current revocation policy, historical counter transition, and uniqueness across ledgers. Do not compare old claims against *current* expiry/counter. Refuse unknown verifier versions until a supported version-specific verifier is installed; retain old verifiers/keys for historic lines. A changed policy/candidate still makes an otherwise valid historical line **stale** for current authority. Synchronous `auditDecisionLedger` may continue checking shape/chain; async `verifyRecord` must additionally report protected-proof verification, not return `CONSISTENT` for forged attested claims. Legacy readers/old bytes remain unchanged when there is no attested line; no new evidence may reclassify v1 or `AUTO` as attested. If the protected registry is unavailable, fail closed for attested lines, including read-only projection and history replay; do not claim that repository-only verification can establish registration provenance or nonce use.

## Append ordering, approve/reject, and group decisions

The integration point is the existing `withModuleLock` recorder path in `record-decision.mjs`, with current candidate reconstruction in `resumable-migration.mjs`. The attested writer is a **separate internal entry**, not a new `--approve`, `ask.channel`, mode, MCP argument, or extension of `buildDecision` accepting arbitrary `principal`. In the lock: assert installed toolkit and format 19, read current trusted policy, rederive candidate via `moduleRecompute`, compare full digest, identity, `requiredPrincipal` and review snapshot, require approvable and group membership equality, check no existing v2 outcome for same digest (including relayed), read verified ledger/head, verify assertion against protected issuance/registry and chosen result, construct the exact one-line v2 decision, atomically claim nonce, durable append, finalize protected claim, then fresh `projectDecisions`. On any failure before claim: no append; after claim: spent and fail closed as above. The current `appendFile` path needs an attested-only durable append/finalize path, without changing v1 serialization. No second lock or partial group append.

An `APPROVED` assertion satisfies **only** the current exact candidate and required trusted policy; it does not advance the checkpoint or bypass other validation. A `REJECTED` assertion is separately chosen, separately signed, and blocks **only** that candidateDigest, becoming stale after evidence, group membership or policy changes. The existing single resolver handles rejection and duplicates/conflicts; extend audit so duplicates for singles **and** groups refuse on read as well as write. No cancellation, browser dismissal, provider decline, timeout or HTTP/IPC loss is interpreted as rejection. A group review yields **one ordered member set, one group candidate digest, one result, one assertion, one v2 line**, and one consumed checkpoint identity. No member-level proof/line, no subset projection as independent authority. A torn/uncommitted group line means none of its members is authorized.

## Exclusions, risks, and blockers

- **Critical / current BLOCKED:** no deployment-specific agent-inaccessible service/admin/browser boundary or real-host proof of UV/UP/review integrity has been accepted. Minimum missing trust primitive: enforced distinct non-admin agent and protected operator/service identities (or equivalent isolated managed OS service/browser boundary) plus verified authenticator UV and protected enrollment/state. Root-owned policy file alone is insufficient. Keep write switch OFF.
- **Critical:** shared operator browser/profile, debugging port, compromised TLS endpoint, or a synced/automatable credential can turn a signed challenge into an agent-driven action. Require host isolation and actual hardware/browser evidence; if operator intent cannot be protected on a proposed platform, BLOCKED for that platform. WebAuthn alone authenticates a credential and UV, not that the human understood the HTML.
- **High:** worktree contents/state/lock/`integrity.json` are agent-writable; their hash chains detect some edits but do not establish writer provenance. Protected claim/credential history and signed payload are mandatory; privilege escalation, protected-store rollback or a forged installed build invalidates the boundary. Audit retention and compromised-key revocation can block existing decisions, deliberately.
- **High:** actual browser secure-context/TLS and RP-ID support, OS-user separation across host/guest environments, hardware key policy/zero-counter behavior, packaged dependency tree and OS service provisioning are **unknown until implementation/acceptance**. No uncertainty is hidden by adding a permissive fallback. Release on Windows is not implied by advisory Windows CI; an unsupported host stays signer-unavailable.
- **Out of scope:** artifact format 14, direct-ledger artifact authority, unrelated migration architecture, module-19 production-default activation, provider-native HUMAN trust, general-purpose identity platform and rewriting old v1 lines/pins. No provider trust experiment, implementation, commit or release is authorized by this plan.
