## 1. Architectural root cause

**Authority is modeled as provenance of the keystroke, not provenance of the
evidence.**

Every gate in the engine answers "may this run?" with some variant of *did a
human type it?*:

| Gate | File | Test it applies |
| --- | --- | --- |
| Self-confirmation | `migration-policy.mjs` `maySelfConfirm` | a per-flag denylist of transitions that "are never self-confirmed" |
| Decision recorder | `operator-approval.mjs` `recorderFor` | `process.stdin.isTTY && process.stdout.isTTY` |
| Decision CLI | `record-decision.mjs` ~980 | `--approve` refused without a TTY |
| Operation sequence | `operation-sequence.mjs` `authorizeOperationSequence` | a challenge phrase a human must retype |
| Option combination | `migration-policy.mjs` `assertOptionCombination` | `--adopt-visual-contract` / `--amend-slice` *throw* under `--mode auto` |
| Unclaimed target drift | `resumable-migration.mjs` `assertNoUnclaimedTargetDrift` | FINALIZE throws unless a human recorded `TARGET_DRIFT_ACCEPTED` |
| Toolkit identity | `toolkit-identity.mjs` `toolkitIdentityBlocker` | refuses until a human runs the adopt command |

A confirmation ID is *integrity* machinery — it binds a preview to the bytes it
previewed, and `assertExecutionConfirmation` re-verifies it. It was reused as
*authority* machinery, which conflates two unrelated questions.

**Why point fixes never converged.** `maySelfConfirm` is written as a denylist:

```js
return mode !== "step" && !refresh && !reopenUi && !reopenComplete
  && !reworkSlice && !adoptVisualContract && !amendSlice && preview?.state !== "NOT_STARTED";
```

Every *new* transition therefore defaults to operator-required, and the only
available fix is to append one more `!flag`. The structure guarantees that the
next feature reintroduces the bug. Same shape at the other gates: `isTTY` is a
property of the process, so any agent-driven run fails it by construction, and
each fix was a per-call-site escape hatch.

## 3. Internally decidable vs genuinely external

**Internally decidable** (items 1–13 above, except legacy refresh in item 12): every one of them is a function of
evidence the engine already holds — the preflight verdict, the confirmation ID
it just minted itself, the slice plan, the decision ledger, the dirty manifest,
the git revision, `build-identity.json`. Nothing about them requires a human to
*know* anything; the human was only ever being asked to *assent*.

**Genuinely external** (must remain a STOP):

- no credentials / no access to a required remote (Figma MCP unreachable, git
  remote unauthenticated);
- a required Figma link that was never supplied — the engine cannot invent a
  URL, and `designSource: figma-mcp` makes it authoritative;
- the running engine is a **source checkout with no `build-identity.json`** — it
  has no identity to prove or stamp, so no evidence exists to decide from;
- a preflight refusal that reports a real defect (missing OpenSpec authority,
  unreadable legacy root, corrupt record, failed gate) — `BLOCKED`, not
  `AWAITING_CONFIRMATION`;
- genuinely ambiguous target drift: a path that is neither inside the
  migration's owned target scope nor outside it in a decidable way.

## 4. Remediation plan

### 4.1 One canonical auto-decision policy

New module `packages/migration-engine/src/auto-authority.mjs`. It is the single
place that answers "is this process the authority for this decision?":

```js
export const isAutoAuthority = (mode) => (mode ?? DEFAULT_MODE) !== "step";
export const autoProvenance = (reason, evidence) => ({ channel: "AUTO", … });
```

`auto` is a *principal*, not an exemption. Every gate listed in §2 consults it
instead of probing a TTY or consulting a per-flag denylist.

### 4.2 Deterministic evidence / provenance rules

Every decision the engine makes on its own authority writes the same shape into
the append-only ledger / history it would have written for a human:

- `channel: "AUTO"` (vs `TERMINAL` / `ELICITATION`);
- the toolkit identity of the engine that decided;
- the digests the decision is bound to (`pathDigest`, `confirmationId`,
  `sequenceDigest`, legacy/target dirty digests) — unchanged, so an auto
  decision is invalidated by a later edit exactly like a human one;
- a machine-written `rationale` naming the evidence.

Authority changes; **integrity does not**. `assertExecutionConfirmation`,
`decisionLineDigest`, the hash-chained history and every pin stay as they are.

### 4.3 Target drift: three classes, not two

`classifyTargetDrift` gains a third answer so "unclaimed" stops meaning
"unrelated":

- **owned drift** — the path is under a planned slice's `targetOwner` subtree,
  or under the module's target scope. Auto-accepts with a recorded
  `TARGET_DRIFT_ACCEPTED` whose rationale names the owning slice.
- **unrelated drift** — the path is outside every owned subtree. Classified
  `UNRELATED_USER_CHANGE`: preserved, never modified, never claimed, and
  excluded from the FINALIZE refusal. It is reported, not owned.
- **ambiguous** — no slice plan exists yet, so ownership cannot be derived.
  Remains a genuine STOP.

### 4.4 Recovery / retry / fallback

`recoverTransaction` already replays an interrupted transaction; what stopped
the loop afterwards was the *approval* gate, not the recovery. With §4.1 in
place, resume continues automatically. `runArtifact` retries the iteration after
an auto-recorded decision instead of only after a TTY one.

### 4.5 Unrelated user changes

`TARGET_DIRTY_SCOPE` exclusions and the `UNRELATED_USER_CHANGE` class are the
whole protection: the engine never writes to a path it has not claimed, and
auto-acceptance is scoped to owned subtrees only.

### 4.6 Regression coverage

One new suite, `test/unit/auto-authority.test.mjs`, plus additions to the
existing suites, covering: bootstrap/resume; `COMPLETE` + legacy drift +
selective reopen; refresh/reopen/rework/amend; target drift with relevant *and*
unrelated files; toolkit identity adoption; evidence invalidation and
re-verification; interrupted transaction recovery; FINALIZE; runtime/provider
transitions; failure/retry/fallback. Plus a **grep gate**: no
`AWAITING_CONFIRMATION` / "Reply Yes or No" reachable under `--mode auto`.

### 4.7 Acceptance criteria

1. `--mode auto` never emits `AWAITING_CONFIRMATION` or `OPERATOR_DECISION`
   for an internally decidable transition.
2. The string "Reply Yes or No" no longer exists.
3. Every auto decision is in the ledger with `channel: "AUTO"`, its evidence
   digests and a rationale.
4. Unrelated dirty target files never block FINALIZE and are never claimed.
5. `--mode step` behaviour is byte-identical to today.
6. Integrity is unchanged: a tampered confirmation ID, a stale digest or a
   toolkit mismatch against a *released* pin still refuses.
7. Remaining STOPs map only to §3's external list.
8. Engine, provider, release-check and integrity gates green; the four provider
   projections regenerate clean.

### 5.2 Done — analysis of the first test run

`pnpm engine:test` fails. The failures inspected so far are **expected
behaviour changes, not defects**:

- `run-migration.test.mjs` "a confirmed bootstrap ends with exactly one
  CONTINUE directive" and "auto reaches the normal run contract" throw
  `Execution confirmation is missing or expired`. Cause: the test helper
  `bootstrapCli` runs the old two-phase dance — phase 1 to read the ID, phase 2
  to pass `--confirm-execution <id>`. Under auto, **phase 1 now executes**, so
  by phase 2 the record exists, the preview differs, and the phase-1 ID is
  legitimately stale. Fix the helper, not the engine.
- `--mode step bootstraps with no directive at either phase` asserts on the
  removed prompt string. Update the expected text to `Mode: step — awaiting
  explicit confirmation.`

**Full count: 39 distinct failing tests** (each appears twice in output — the
`engine:test` script runs an unidentified pass and an identified pass). They
fall into three groups, and only the first is a straightforward rewrite.

**Group A — expected behaviour change, rewrite the assertion.** The two-phase
bootstrap collapsing to one phase; the removed prompt string; `registration is
never self-confirmed, in any mode`; `R-W3-c: --rework-slice under --mode auto
is refused`; `--reopen-ui is operator-only and exclusive`; `maySelfConfirm
reproduces every verdict the wrappers computed`; the step-mode stop tests
(text only — step behaviour itself must stay byte-identical, verify that).

**Group B — possible real regression, investigate before touching.** The four
`R-1 proof (ancestor|legacy|spaced|unrelated): the engine resolves the consumer
registry, not its own ancestor` tests have nothing to do with approval. The
likely cause is the new `autoAdoptToolkitIdentity` call added to the discover
CLI: it calls `readContext`/`readState` on a path that previously was not
touched there, so it may resolve or throw differently. Check this first — if
`autoAdoptToolkitIdentity` is the cause, the wiring is wrong, not the test.

Also in this group: `an MCP run never falls back to the transport's own TTY`.
`recorderFor` now returns the auto recorder *before* honouring an explicit
`recordTrustedDecision: null`, and the MCP adapter passes exactly that `null`
to declare "this client has no human channel". The reorder overrides a
deliberate declaration. Probable fix: let an explicit `null` win over auto, and
have the MCP adapter opt into the auto principal by mode instead.

**Group C — a security-posture decision, not a test bug. Needs the owner.**
About a dozen tests exist specifically to prove *the agent can never approve*:
`run-migration.mjs cannot forge a TTY or hardcode a verdict`; `no sequence of
tool calls appends to the operator decisions ledger`; `no run invocation
without a TTY ever writes the operator decision ledger`; `an agent cannot mint
its own artifact approval`; `with no TTY run prints each candidate's own
command and writes nothing`; `a run against a pending operator decision stops
at OPERATOR_DECISION without approving`; `pending operator decisions block
advance and no approval API exists on the engine`; `without elicitation the
same migration_run refuses to approve the delegated decision`; `a host that
cannot deliver a human answer still leaves a trusted worktree-scoped path`; and
the toolkit-identity set (`an installed toolkit refuses to mutate an unstamped
record and names one command`, `... only after explicit adoption`, `only the
pinned build may mutate`, `a different build is refused by every mutating entry
point`).

These encode a threat model with an explicit rationale in the source: a
non-empty string is not an approval, and an agent must not be able to author
one. The task asked for exactly the inversion of that under `--mode auto`, and
the implementation delivers it — but "rewrite the tests that exist to prevent
this" is a decision about what the toolkit guarantees, not a mechanical fixup.

Before rewriting Group C, get an explicit decision on the intended posture:

- Is `AUTO` an acceptable *third principal* — i.e. the guarantee becomes "an
  agent cannot approve while impersonating a human; it approves as itself, on
  the record, and `step` remains available when a human is required"? That is
  what is implemented, and it is defensible: every `AUTO` line names its
  channel, so an unattended approval is auditable as one.
- Or must some subset stay human-only even under auto — most plausibly the
  toolkit-identity gate across a *major* version change, and
  `TARGET_DRIFT_ACCEPTED` for owned-but-unclaimed bytes?

Whichever answer, record it in this file before editing those tests, so the
next reader can tell a deliberate posture change from an eroded one.

### 5.2a Group C — the decided posture (2026-09-23)

**AUTO is a distinct trusted workflow principal, not a simulated human.** The
owner decision, recorded here before the tests were touched, as §5.2 asked:

- providers/agents may never forge, synthesize or append a human approval;
- `decisions/operator-decisions.ndjson` stays **human-only**. AUTO writes to its
  own `decisions/auto-decisions.ndjson` -- same line shape, own hash chain, own
  `integrity.json` anchor, `AUTO-` id prefix so a citation can never be read as
  a human one. `readOperatorDecisions` refuses a line claiming `AUTO`;
  `readAutoDecisions` refuses one that does not. Lookup unions the two; nothing
  merges them on disk;
- every AUTO line records `principal`, `decisionType`, `evidence`, `scope`,
  `result`, and the deciding build's toolkit identity;
- ambiguity is never auto-decided. Target drift with no derivable owner is
  marked `autoResolvable: false` and refused to AUTO at the one approval gate;
- toolkit identity: AUTO adopts an **unstamped** record or a **strictly newer**
  release of the same toolkit (`autoAdoptableToolkitTransition`). A downgrade, a
  different toolkit, or the same version with a different commit/contentHash is
  BLOCKED -- never approved around;
- `--mode step` keeps human confirmation semantics byte-for-byte.
