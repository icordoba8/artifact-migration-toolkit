## Gate result

**G1 — GAP: the installed toolkit's MCP registration cannot be consumed by Copilot CLI.**
- At BASE, the Copilot payload registers `start-migration` only in `.vscode/mcp.json` with the VS Code `servers` key and no `tools` or `env` fields (`providers/install-support.mjs:23`, `providers/copilot/adapter.json:31`, `providers/copilot/mcp.json`). The skill runtime re-asserts that location on every run.
- Copilot CLI 1.0.105 loads MCP only from `~/.copilot/mcp-config.json`, `.mcp.json`, `.github/mcp.json` or plugins (H/sub-mcp.txt:9-12). D1 says `.vscode/mcp.json` must be migrated to `.mcp.json` (`servers`→`mcpServers`). D1 also makes `tools` **required** for local servers.
- The toolkit documents this itself: "Without a connected server Copilot CLI uses the CLI fallback" (`providers/copilot/skills/start-migration/references/provider-compatibility.md:28-30`). In that fallback the engine runs over shell with **zero** MCP grants, so "exactly 9 MCP grants (no `migration_relay_decision`)" cannot hold.
- The only adapter-level workaround would be harness-authored server registration (`--additional-mcp-config`). That repairs the installed toolkit, which the run contract forbids ("do not repair or modify the installed toolkit"), and it would hide a payload defect that every real Copilot CLI user hits.
- Root-cause fix: change the provider payload/runtime registration (skill/receipt territory, new release candidate). That is out of P1 scope, so it goes to separate task T1.
- An owner ruling could accept harness-authored MCP registration for Copilot CLI. G1 would then become ADAPTER_NEEDED (S), and no other GAP remains. This document does not make that ruling.
