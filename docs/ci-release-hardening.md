# CI and Release Architecture

## Goals

Catch failures before release preparation. A release starts from one exact SHA
whose development CI has **run and succeeded on Ubuntu**. Packaging proves the
built artifact; it does not rediscover source portability.

Ubuntu is the only required CI and release platform. Windows CI is not part of
routine CI and is not required for publication. See *Windows CI status* below.

## Development CI

`.github/workflows/ci.yml` runs on every branch push and pull request. The
`ubuntu` job runs as three parallel shards (`toolkit shard N/3 (ubuntu-latest)`). `providers:test` is split **per test file**
into `providers:test:1..3` (never within a file); every shard first asserts the
three lists partition `providers:test` exactly, and shard 3 also runs the engine
suites. The `toolkit` job, named `toolkit (ubuntu-latest)`, needs every Ubuntu
shard, runs `if: always()`, and succeeds only when `needs.ubuntu.result` is
`success` — so it stays the one required check:

| Gate | PR | Main | Release SHA | Reason |
| --- | --- | --- | --- | --- |
| Frozen pnpm install | yes | yes | yes | lockfile and dependency topology |
| `pnpm providers:check` | yes | yes | yes | generated bytes agree |
| Consumer-relative path scan | yes | yes | yes | installed engine path safety |
| `pnpm providers:test` | yes | yes | yes | providers, release fixtures, installed acceptance |
| `pnpm rehearse`, `pnpm rehearse:negative` (shard 2) | yes | yes | yes | installed lifecycle replay against the golden trace |
| `pnpm architecture:check` (shard 3) | yes | yes | yes | module boundaries and source pins |
| `pnpm engine:test` | yes | yes | yes | engine and external acceptance |
| `pnpm engine:test:ts` | yes | yes | yes | TypeScript filesystem/recovery |
| `pnpm release:check` | no | no | after green CI | clean SHA, version, immutable content identity |
| Build, verify, installed smoke | no | no | after `release:check` | packaged artifact |

Every CI row above runs on Ubuntu. No step or job has `continue-on-error`, so a
failed command names its step and the job concludes red.

The published 1.3.4 version may remain in the manifest during ordinary
development; changed payload bytes correctly make `release:check` fail until a
new version is chosen. It therefore is a release gate, not a development gate.

## Windows CI status

**Removed from routine CI. Not required for release. Not validated.**

The repository owner stopped investing in Windows CI stabilization: its
execution time and recurring failures were disproportionate to Ubuntu. There is
no Windows job in `.github/workflows/ci.yml`. Windows execution is not required
for publication, and a missing or failing Windows result cannot block a release.
This is not a claim that Windows works: no release has been proven against a
fully green Windows matrix, and no release note may say Windows compatibility
was validated.

History, kept as evidence:

- Windows failed before `engine:test` for most of its history. Commit 9a328f9
  fixed that harness blocker; `engine:test` then exposed 9 further pre-existing
  portability failures.
- Run 38171795578 (21e9e48): Windows shards 1/3 and 2/3 green, shard 3/3 red
  with a 24-test `engine:test` backlog (crash-at, companion, signer, WebAuthn).
- The job was paused (commented out) during Track A and restored as advisory
  (`continue-on-error`) in b71c949. Run 38305916236 (b71c949): shards 1/3 and
  2/3 green; shard 3/3 red on two `test/architecture.test.mjs` cases
  (`Cannot find module 'ts-discovery-compiler'`), so `engine:test` and
  `engine:test:ts` never ran.
- An unmerged fixture fix (0c53c4e, run 38310673521) let shard 3/3 reach
  `engine:test`: 25 failures (the 24 above plus one `formats.test.mjs`
  quoted-path assertion). `engine:test:ts` has never run on Windows. That fix
  was not adopted.

### Reconsidering Windows CI

Windows may return only as a separate, explicitly authorized task. No Windows
remediation work is authorized now. Before Windows CI is added back in any
form, all of these must hold, deliberately verified by a human:

1. the complete Windows matrix passes, including `providers:check`, the
   consumer-relative path scan, every `providers:test` shard, `rehearse`,
   `rehearse:negative`, `architecture:check`, `engine:test` and
   `engine:test:ts`;
2. no required suite is hidden, skipped, quarantined or allowlisted — only the
   documented OS-capability skips in *Platform-specific tests* remain;
3. measured total Windows execution time is no more than five minutes longer
   than comparable Ubuntu CI;
4. the evidence comes from **two independent** CI runs (different commits, not
   reruns of one).

## Cross-platform testing rules

- **Path identity:** use filesystem `realpath` on both sides of an identity
  comparison. Do not lowercase paths or compare a caller's short path with Git's
  long path. `dirtyManifest` owns this in product code.
- **Serialized paths:** edit the parsed value where possible. For the generated
  JSON-compatible TOML string, use `replaceSerializedPath`; it asserts the
  encoded target exists and the bytes change. Every negative tamper must assert
  it changed its input.
- **Line endings:** decide whether the assertion is byte identity or textual
  equivalence. Hashes, release payloads, and generated runtime copies require
  exact bytes; `.gitattributes` pins text checkout to LF. Normalize CRLF only
  at a comparison of genuinely equivalent text, never before hashing.
- **Dependencies:** scratch roots link each declared external dependency to
  its resolved store path. Never junction an entire pnpm `node_modules` tree or
  link its workspace package back to source.
- **Consumers:** use unique temporary roots and distinct store, receipt, and
  record paths. Never rely on a shared global temp listing for isolation proof.
- **Locks:** an awaited lock poll retains a referenced timer until it settles.
  Concurrency regressions must observe contention, completion, release, and
  absence of leaked locks; do not use `unref()` on the required poll timer.
- **Commands:** inject an executor into tests that need a failing command.
  Do not rely on extensionless PATH shadowing or modify process-wide PATH.

## Platform-specific tests

These describe the test code's own platform handling; CI does not execute the
Windows branches.

POSIX permission-mode tests in `test/runtime-bootstrap.test.mjs` and
`test/providers-sync.test.mjs` skip on Windows (and as root): Windows ACLs do
not implement `chmod 0o555` as an unwritable directory. Other doctor blockers
and ownership conflicts are not platform-gated. Provider directory
junction safety runs on Windows; file-symlink tests run if the Windows runner
can create them and skip with an explicit capability reason otherwise. No
product behavior is globally skipped on Windows.

## Shared test infrastructure

`packages/migration-engine/test/support/dependency-links.mjs` links declared
external dependencies for the candidate release root and the isolated engine
runners. `candidate-release-root.mjs` owns synthetic release payload/version
construction. `serialized-path.mjs` owns encoded path tampering.
`portability.mjs` owns the test side of the Windows boundary: `comparisonPath`
for asserting on rendered paths, `renderedCommandPattern` for asserting on a
command `engineCommand` rendered (quoted or not, either separator), `stopChild`
to await a child's exit before its cwd is removed, and `removeTree` for bounded
`fs.rm` retries.
`scripts/test-isolation.mjs` copies the source into a unique scratch checkout,
then links only external dependencies; the source and test identities remain
separate. Add a helper only when a second real caller needs the same mechanism.

## Release preconditions

The candidate and final version commits each need, on their **own exact SHA**:

- `ci / toolkit shard 1/3, 2/3, 3/3 (ubuntu-latest)` = **executed and
  SUCCESS** on that SHA, and `ci / toolkit (ubuntu-latest)` = **SUCCESS**.
  Required. A red or missing Ubuntu result means the SHA is not release-ready,
  with no exceptions. Release and version commits carry no
  `CI-Validated-Review` trailer, so CI reuse never stands in for them.
- Windows: not required. The release report states `WINDOWS CI: NOT_RUN (not
  required)`.

Never call a SHA with red Ubuntu release-ready. Configure GitHub branch
protection on `main` to require exactly one status check:
`ci / toolkit (ubuntu-latest)`. Repository code cannot configure branch
protection. No workflow or local script verifies remote check status; the
release operator must read all three Ubuntu shard conclusions and the gate for
the release SHA before running `release:check`.

## Release validation

On the green, clean release SHA: `pnpm release:check`; `pnpm release:build`;
`pnpm release:verify <staged-dir>`; one installed smoke of that staged bundle.
Only then publish the immutable asset and run `pnpm release:record <version>`.
`release:check` refuses an established version with changed payload bytes.

## What must not be repeated during release

Do not rerun `engine:test`, `engine:test:ts`, `providers:test`, or
`providers:check` as a routine release-stage ritual for the same SHA. Their
Ubuntu results are development CI evidence. Rerun a focused gate
only when its input changes; that change creates a new SHA requiring CI again.

## Troubleshooting red CI

Identify the first failing step and platform; classify product behavior, shared
test infrastructure, one-off test mechanism, or genuinely platform-specific
semantics. One rerun may distinguish a suspected infrastructure flake. A second
identical failure is reproducible: fix its owner or stop. Do not keep rerunning
for green, add arbitrary timeouts, or sleep to hide races.

## Adding a new platform-sensitive test

Add its file to the explicit `package.json` runner list. Decide byte identity
versus text equivalence, use canonical paths for identity, assert negative
tampering happened, use the shared dependency and fixture helpers, and keep
consumer state in unique temporary roots. Normal CI tests it on Ubuntu.
Skip only a documented unavailable OS capability or semantic with alternate
cross-platform coverage.
