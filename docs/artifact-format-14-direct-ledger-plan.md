# Artifact Format 14: Direct-Ledger Artifact Decision Authority

> Historical implementation plan. Current defaults are Module 19 and Artifact 14,
> with self-contained STANDARD_LOCAL / AGENT_RELAYED decisions. Pilot-only and
> mandatory-signer statements below describe the earlier milestone and are
> superseded by the [current architecture](../README.md#architecture).

## 1. Goal and non-goals

Implement a deliberately selected, supported artifact format 14 with the same decision security boundary as module format 19 where the semantics are shared: current artifact candidate -> complete engine-owned review -> trusted policy -> verified ledger result -> fresh projection -> artifact validation -> identities consumed by a journalled checkpoint. Cover both source-inventory `operatorDecisions` and visual `VISUAL_UNBACKED` exceptions. An approval does not itself advance a checkpoint or replace structural, source, visual, runtime, or target verification.

Do not change the meaning or bytes of artifact 13, activate artifact 14 as the ordinary creation default, implement/activate WebAuthn or a signer, activate module 19 by default, redesign providers or Windows CI, perform real-host acceptance, execute a v1.3.7 release, or clean unrelated migration state. This is a plan, not implementation approval.

## 3. Security invariants

**Decision authority.** Format 14 accepts exactly one applicable, verified v2 ledger outcome for the *current* candidate: `APPROVED` authorizes the decision gate; `REJECTED` blocks it. A line's hash chain is integrity evidence, not human-authentication evidence. The authored source inventory and visual matrix propose questions; neither their `decisionId`/`decisionDigest`, text, nor a copied `recordedDecisionId` is approval authority. V1 lines and legacy AUTO do not become attested v2 authority.

**Candidate and evidence binding.** Derive full SHA-256 candidate identity from record kind/ID and target root, current source revision/dirty/manifest and target binding where relevant, artifact workflow/lifecycle/checkpoint, kind, subject, rationale, targets, and the current validated source-decision row or visual unbacked row with its reason, required behavior/state, visual authority/context/frame and pinned evidence digests. Compute a canonical digest of those *decision-bearing* facts, not a free-form `APP-` ID, synthetic format number, or untrusted claimed digest. Recompute evidence under the artifact lock before append and again before advance; changed source, visual evidence, policy, membership or lifecycle makes the old line non-applicable. Do not make an approval substitute for existing `validateSourceInventory`, `validateBoundTo`, visual context, or screenshot/observation checks.

**Policy/principal binding.** Reuse `resolveRequiredPrincipal` and the v2 `policyId`/`policyDigest`/`requiredPrincipal` candidate binding. The existing `ARTIFACT_DECISION` and `VISUAL_UNBACKED` defaults require `HUMAN_ATTESTED`; only a protected operator/admin policy with valid provenance may explicitly authorize `AGENT_RELAYED`. AUTO is a distinct engine-owned principal/ledger, never inferred from `--mode auto` to satisfy a stronger requirement. Repository documents, argv/env, providers, MCP and authored state cannot downgrade it. Preserve existing hash chains and any applicable prefix/anchor enforcement; add format-14 artifact checkpoint anchors for consumed ledger bytes without rewriting historical prefixes.

**Stale and rejected behavior.** Status and pending distinguish never decided, applicable approval, current REJECTED, and STALE after evidence/policy change. Rejection applies to the exact candidate only; dismissal, timeout, transport failure or host decline writes no rejection. Duplicate or conflicting applicable entries and malformed/torn chains fail closed rather than selecting the first/newest. A valid historical line is not current authority if its evidence changed.

**Group atomicity.** If multiple homogeneous decisions at one artifact checkpoint are grouped, use `createNewFormatDecisionGroup`: one ordered, fully evidence-bound group candidate, one review, one v2 ledger line/result, one authority for all members. Never combine source and visual checkpoints into a group or accept a member line as a substitute. Any changed/missing/extra member or incomplete append invalidates the entire group; do not group if the artifact decision source cannot provide stable complete membership under lock.

**Consumed identities.** A format-14 advance journals each actually consumed `{candidateDigest, decisionId, decisionDigest, policyId, policyDigest, principal, result}` once (one identity per group) in its transaction and hashed `ADVANCED`/`COMPLETED` event; replay rederives and checks the same set and verified ledger-prefix anchors before publication. A read-only projection never records consumption. Keep format-13 transaction version, event shape, history and fixture bytes unchanged.

**Signer unavailable.** Current readers reject `HUMAN_ATTESTED` without a replay verifier and current writers cannot mint it. Format-14 candidates requiring that principal surface `SIGNER_UNAVAILABLE` (or the existing equivalent typed blocked state) and do not advance. No TTY approval, MCP-as-human, provider-native human trust, env/argv approval, repository policy downgrade or automatic fallback to `AGENT_RELAYED`.

## 5. Target architecture and ownership

Reuse existing functions instead of building a parallel artifact ledger. `createDecisionCandidate` remains the v1 candidate builder; format 14 uses `createNewFormatDecisionCandidate` (policy binding and digest) and, only for stable homogeneous groups, `createNewFormatDecisionGroup`. `resolveApplicableDecision`/`projectModuleDecision` supply the shared v2 outcome semantics, but must be exposed through a record-neutral entry or thin artifact adapter that passes an artifact-owned current candidate and ledger rows; do not call module state/classification derivation for a child. The name `projectModuleDecision` reflects its current API, not artifact ownership. Reuse `readRecordedDecisions`, `decisionLineProblem`, ledger-chain and principal checks, protected `resolveRequiredPrincipal`, `reviewFor`/`renderDecisionReview`, and the locked `record-decision.mjs` append path. Preserve the lazily imported artifact engine in `deriveArtifactDecisions` to avoid a static ESM cycle. `buildDecision` currently writes only v2 `AGENT_RELAYED`; this milestone does not broaden it to attested claims. Preserve separate legacy/AUTO serialization and do not permit a v1/AUTO line to satisfy a format-14 judgment.

Artifact ownership stays in `artifact/artifact-migration.mjs`: format admission/creation/upgrade, source/target binding capture, source row and visual row/evidence derivation, checkpoint grouping/lifecycle, artifact-specific schema rules, structural/visual validation, status and advance transaction/replay. In particular, format-14 source/visual documents reject forged receipt fields (`decisionId`, `decisionDigest`, `recordedDecisionId` as applicable); those fields remain legal and meaningful in 13. `strictVisualState` can still adapt the shared *evidence* checks, but must not decide artifact-14 authority by pretending the artifact is a module 19: inject/use the same shared v2 resolver at the visual decision gate while keeping evidence validation unchanged. Artifact decisions stay recorded by `record-decision.mjs`, not by an agent-authored JSON file or a new artifact-only writer.

**Proposed artifact projection** (implementation name not yet an existing API): derive current source or visual candidates after read-only structural checks, trusted policy and both verified ledgers, resolve through the shared outcome, and return `AWAITING_HUMAN_DECISION`, `APPROVED_APPLICABLE`, `REJECTED`, `STALE`, `READY_TO_ADVANCE` or `LEGACY_COMPATIBILITY_ACTION_REQUIRED`, `blocked: SIGNER_UNAVAILABLE` where applicable, and `checkpointAdvanced` separately. `getArtifactStatus`, artifact pending output from `runRecordDecisionCli --artifact --pending`, and `runArtifactIteration`/`runArtifact` consume **that one fresh view**; running still revalidates under lock and may execute target checks, status/pending never does. Audit-only decision IDs/digests may appear in projection/history; they are not instructions to copy receipts. A successful append is visible on the next projection in the same session even before checkpoint advance. Legacy 13 continues on its current path.

## 8. Release impact and blocking risks

**Release:** after implementation and review, format 14 changes persisted schema, engine behavior and a supported-format manifest; ship only in a **new toolkit release** after the repository's version-discipline, format-registry, package/provider generation, staged build/verify, engine/TS/provider tests and release checks succeed. Only at the later CLEAN, COMMITTED release-candidate stage run `pnpm release:check`, `pnpm release:build`, and `pnpm release:verify <staged-directory>`; none is an implementation-phase gate. Obtain separate release approval; this plan makes no version/CI/release change. Ubuntu CI is **REQUIRED**; Windows CI remains **ADVISORY** until an explicit user instruction changes it. No claim that Windows advisory results activate a signer.

**Blocking risks:** (1) The artifact visual adapter forces module-format-17 evidence semantics; routing 14 through it without a format-aware authority gate could accept a 13 citation or skip the visual decision. (2) A line in an agent-writable hash chain is not authenticated human intent; `HUMAN_ATTESTED` remains unavailable until the separate signer, isolated deployment and real-host gates in `docs/operator-decision-signer-webauthn-plan.md`. (3) Artifact history/event schemas and replay are strict; a 14 identity field written without a version-gated replay proof would make crash recovery diverge or mutate 13 bytes. (4) A module-19 parent can observe a 13 child, but cannot reinterpret child legacy citations as v2 authority. (5) A broad 13 -> 14 conversion would silently promote already-authored/pinned decisions; reject it rather than inventing authority.

**Signer boundary:** format-14 schemas, candidates, protected policy resolution, ledger reader/resolver, review, blocked projection, tests, journal and explicit pilot creation can all be completed with `HUMAN_ATTESTED` writes **OFF**. Positive `AGENT_RELAYED` decisions are possible only where a genuinely protected admin policy explicitly allows them; this is not a downgrade triggered by signer absence. If no such policy is available, judgment-bearing pilots remain blocked, which is correct support behavior. Do not claim practical attested approval, general production usability, human signer activation or production-default 14 creation until a separate approved signer/security/release milestone succeeds. Artifact 14 support does not imply `HUMAN_ATTESTED` availability.
